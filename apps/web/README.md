# Web

Next.js (App Router) + TypeScript frontend. Requires Node.js 24 (`.nvmrc`); pnpm is pinned in `package.json` and provided by corepack.

From the repository root:

```sh
make web-setup    # install locked dependencies
make web-check      # format check, lint, type check, tests, production build, bundle and runtime auth checks
make web-dev        # development server on http://localhost:3000 (no sign-in: needs https)
make web-dev-https  # development server on https://localhost:3000 with sign-in
```

## API boundary

Only server-side code in `src/lib/api/` calls the API. It reads the server-only `API_BASE_URL`, validates every response, and reports failures explicitly (`not-configured` or `unreachable` with a reason) rather than assuming success.

## Authentication

Sign-in uses OpenID Connect Authorization Code + PKCE against the configured provider (Auth0 in development), as a confidential client on the Next.js server. The browser only ever holds two sealed, HttpOnly cookies; tokens never reach client code.

| Route                            | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /auth/login?returnTo=/path` | Creates state, nonce and a PKCE (S256) verifier, stores them in the sealed `__Host-oidc` cookie (10 minutes), clears any current session, and redirects to the provider with `scope=openid` and the API audience.                                                                                                                                                                                                                                                                                                     |
| `GET /auth/callback`             | Requires the transaction cookie; openid-client checks state and PKCE and validates the ID token's claims (issuer, audience, expiry, nonce; RS256 only; its signature is not checked because it comes directly from the token endpoint over TLS, as OpenID Connect Core 3.1.3.7 allows). On success it replaces any session with a new `__Host-session` cookie and redirects to `returnTo` (same-origin relative paths only). Any failure clears both cookies and shows a fixed error page; only a category is logged. |
| `POST /auth/logout`              | Only with `Origin` equal to `APP_ORIGIN` (otherwise 403; GET is 405). Clears the cookies and redirects to the provider's end-session endpoint, which returns to `APP_ORIGIN/`.                                                                                                                                                                                                                                                                                                                                        |
| `GET /account`                   | Shows `GET /v1/me` for the signed-in user; the API is called server-side with the access token as a bearer token.                                                                                                                                                                                                                                                                                                                                                                                                     |

- **Session:** the sealed cookie (iron-session) holds only the access token, its expiry and the creation time: no refresh token, ID token, email or name. It lasts as long as the access token (capped at one hour) and is not renewed; afterwards the user signs in again (silently while the provider's session lasts). A stolen cookie is usable until the token expires, even after logout (accepted trade-off, decision D-A20).
- **Cookies:** `__Host-session` and `__Host-oidc`: `Secure`, `HttpOnly`, `SameSite=Lax` (the provider returns with a cross-site GET), `Path=/`, no `Domain`.
- **Invalidation:** Server Components only read the session. A missing, expired or API-rejected session redirects to `/auth/login`, whose route handler response clears the cookie. If the API rejects a session less than a minute old, the page shows an error instead of redirecting, so a configuration mismatch cannot loop through the provider.
- **Content-Security-Policy:** `src/proxy.ts` sets a policy with a fresh nonce on every page and route response (`script-src 'self' 'nonce-…' 'strict-dynamic'`, `style-src 'self' 'nonce-…'`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'` plus the provider's origin, because browsers apply `form-action` to the redirect after the sign-out POST). No `'unsafe-inline'`; `'unsafe-eval'` only in development. Next.js applies the nonce to its scripts; this needs dynamic rendering, so the root layout forces it. The proxy does no authentication. The app provides its own 404 page (Next.js's built-in one renders inline styles in the server HTML, which the policy blocks) and its own error boundaries (`app/error.tsx`, `app/global-error.tsx`, the tenants `error.tsx`) without inline styles or error details; in production a render error returns a minimal error document with nonce'd scripts and the boundary renders in the browser. Residual: Next.js's static `500.html` fallback is built at build time and cannot carry a per-request nonce; it is served only when rendering fails outside React (not for ordinary render errors), and there its styling would be blocked (text stays readable). There is no App Router file convention to replace it. Every response also has `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Permissions-Policy` and `Cross-Origin-Opener-Policy: same-origin`. HSTS is left to the production front end.
- **Headers:** `/auth/*` and `/account` are `Cache-Control: no-store`. `/auth/*` sends `Referrer-Policy: no-referrer`; `/account` sends `same-origin`, because under `no-referrer` browsers send `Origin: null` on the page's own sign-out POST and the Origin check would refuse it. The development server does not log `/auth/callback` URLs (they carry the authorization code).
- **Configuration** (server-only; see `.env.example`, values in the gitignored `.env.local`): `APP_ORIGIN` (https), `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_AUDIENCE`, `SESSION_SECRET` (at least 32 characters), optionally `SESSION_SECRET_PREVIOUS` during key rotation. With invalid configuration the auth routes answer 503 and the rest of the site works.
- **Provider settings:** callback `APP_ORIGIN/auth/callback` in Allowed Callback URLs and `APP_ORIGIN/` in Allowed Logout URLs.
- **Local HTTPS:** `make web-dev-https` (bound to localhost only) creates a self-signed certificate with openssl in `.local/web-tls/` and serves https://localhost:3000; the browser warns once. It never installs a certificate authority (plain `next dev --experimental-https` would download mkcert and add one to the system trust store).
- **Checks:** unit and handler tests run the real openid-client against an in-process fake provider (state, nonce, issuer, audience, `alg: none`, expiry, missing tokens, provider errors, logout origin). After the build, `check:bundle` fails if auth code or secrets reach `.next/static`, and `check:runtime` starts the production server and checks redirects, headers, methods and cookie clearing end to end (no real provider is contacted).

## Tenants and workspaces

`/account` lists the user's memberships (from `GET /v1/me`); each links to `/tenants/{tenantId}/workspaces`. The tenant is only ever in the URL: there is no "current tenant" cookie or client state. The web app does not decide who may see a tenant: every page and form calls the API with the user's token, and the API checks the membership on every request.

| Route                                        | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /tenants/{tenantId}/workspaces`         | Lists the tenant's workspaces (name and creation time) with a form to create one. Empty tenant: "No workspaces yet". API unavailable: an error with a retry link. Unknown tenant, a tenant the user is not a member of, or a malformed ID: the same 404 page (a malformed ID never reaches the API). No or expired session: sign-in, then back.                                                                                                              |
| `POST /tenants/{tenantId}/workspaces/create` | The form's target (GET is 405). Requires `Origin` equal to `APP_ORIGIN` (otherwise 403, nothing is sent to the API), a session and a form body of at most 8 KiB; the name must be 1 to 200 characters after trimming spaces (the API's rule; the API stays authoritative). Always answers with a redirect back to the list carrying a fixed code (`created=1`, `error=invalid_name`, `error=unavailable`, `error=rejected`); submitted text is never echoed. |

- **Pages** use no client-side JavaScript of their own (only the generic error boundary and, on the workspace page, the upload form's progress state). Messages after a create are fixed texts looked up from the code; unknown codes render nothing. Success uses `role="status"`, errors `role="alert"`; the name field has a label, `required`, `maxlength=200`, a hint via `aria-describedby`, and `aria-invalid` plus the error text when rejected.
- **Headers:** `/tenants/*` is `Cache-Control: no-store` with `Referrer-Policy: same-origin` (the page posts a form; see the `/account` note above).
- **No loading screen:** navigation is by full page loads; a streamed loading screen would force a `200` status before the page can answer `404` or redirect, so there is none.
- **Known limits:** tenants are shown by ID (the API has no tenant names yet); a double submit can create two workspaces (the API has no idempotency key); after a rejected name the field is empty again; no pagination.

### Manual verification checklist

Run against the development stack (API on :8000, `make web-dev-https`, a signed-in test user):

1. **Browser:** `/account` shows each membership as a link; the link opens the tenant's workspaces; creating "Quarterly reports" returns to the list with "Workspace created." and the new entry; submitting only spaces shows the name error next to the field; editing the URL to another tenant ID or `not-a-uuid` shows "Tenant not found"; with the API stopped the page shows the unavailable message.
2. **Keyboard only:** Tab reaches the back link, the name field and the button in order; the focus outline is always visible; Enter in the field submits; nothing needs a mouse.
3. **VoiceOver (macOS: Cmd+F5):** headings read "Workspaces", "All workspaces", "Create a workspace" (VO+U → Headings); the field is announced as "Name, edit text, required" with its hint; after a create, "Workspace created." is announced; after a rejected name, the error is announced and read with the field; the list is announced as a list with its item count.
4. **Zoom and colours:** at 200 % browser zoom nothing overlaps or needs horizontal scrolling; in dark mode text stays readable; errors are identifiable without colour (text and bold).

## Documents

Workspace names on the list link to `/tenants/{tenantId}/workspaces/{workspaceId}`. As everywhere, the API decides membership on every call; the web routes hold the user's token server-side only. Files are stored and returned exactly as uploaded; there is no preview. Document names link to the document page (see "Document processing").

| Route                                                    | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /tenants/{t}/workspaces/{w}`                        | Workspace name, its documents (name, size, upload time, first 12 hex digits of the SHA-256 with the full hash as a tooltip, the API's malware-scan status (Clean / Not scanned / Blocked), and a download link only for Clean versions) and the upload form. Empty: "No documents yet". API unavailable: an error with a retry link. Unknown workspace, non-member tenant or malformed ID: the uniform "Workspace not found" 404 (a malformed ID never reaches the API).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `POST /tenants/{t}/workspaces/{w}/documents/upload`      | The form's target (GET is 405). Checks, in order: `Origin` equals `APP_ORIGIN` (else 403, nothing read or sent), ID format, session, membership and workspace (asked of the API with `GET …/workspaces/{w}` before any of the body is read; a non-member or an unknown workspace gets the uniform 404 page, even if the file is also too large or invalid), `multipart/form-data`, body at most 20 MiB + 64 KiB (declared and counted while reading), exactly one non-empty `file` part of at most 20 MiB. The bytes go to the API unchanged, with the browser's type and the percent-encoded name as hints; the API checks size, the `%PDF-` signature and the name. Always answers with a redirect back to the page carrying a fixed code (`uploaded=1`, `error=too_large`, `not_pdf`, `invalid_name`, `missing_file`, `unavailable`, `rejected`, and for the API's malware scan `malware_detected`, `scan_incomplete`, `encrypted_pdf`, `scan_unavailable`, or `upload_rejected` for an unknown 422 reason, never `invalid_name`); nothing submitted is echoed. |
| `GET /tenants/{t}/workspaces/{w}/documents/{d}/download` | Streams the stored bytes from the API as `application/pdf` with the API's `Content-Disposition: attachment` (anything else is refused with 502), `nosniff`, `Content-Security-Policy: sandbox; default-src 'none'` and `no-store`. Unknown document or no access: 404. A version that is not clean (API 409): back to the page with `error=not_scanned` or `error=blocked` and a fixed message. No session: sign-in, then back to the workspace.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

- **Proxy:** both document routes are excluded from `src/proxy.ts`. With a proxy, Next.js buffers request bodies up to 10 MB and truncates the rest, and the proxy's page CSP would replace the download's sandbox policy. `make web-check` verifies both through `next start` (a 12 MiB upload arrives byte-identical; the download keeps its headers). Details and deployment limits: [`docs/deployment-security.md`](../../docs/deployment-security.md) section 2.
- **Accessibility:** the form works without JavaScript; with it, submitting disables the button ("Uploading…") and announces progress in a `role="status"` region, which also prevents double submits. After a failed upload the error is shown next to the file field as an alert (`role="alert"`, announced on load), tied to the field with `aria-describedby` and `aria-invalid` (explicitly `false` until an upload error or a refused empty submit: with only `required`, browsers announce the empty field as invalid on arrival); it has no timer and stays until the user chooses another file or submits again (page-level errors such as a rejected sign-in stay at the top). The file input is labelled, `required`, limited to PDFs in the picker (`accept`) and described by a hint. The table has a caption, column and row headers and a machine-readable `<time>`; each download link carries the document name as visually hidden text.
- **Malware scanning:** the API scans every upload and decides; the web app only shows the API's outcome and scan status (it never scans or calls the scanner), and offers downloads only for Clean versions (the API refuses the rest with 409 anyway). See `apps/api/README.md`.
- **Known limits:** members can send up to 20 MiB per request (edge rate and volume limits required). Uploads are held in memory by the web server during the request. No pagination, deletion, renaming or versions beyond the first.

## Document processing

Each document has a page at `/tenants/{t}/workspaces/{w}/documents/{d}` showing its metadata, malware-scan status, processing status and, once processing has finished, the extracted service-agreement record. Processing is deterministic and rule-based and runs in the API's worker (see `apps/api/README.md`, "Processing"); the web app only starts it and shows the API's answers.

| Route                            | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET …/documents/{d}`            | Server-rendered. Name, size, upload time, short SHA-256, scan status, a download link for Clean versions, and the processing state in words. Never processed and clean: a Process document form. Finished: the record, one row per field (label, formatted value, source pages); a row with evidence opens (native `<details>`) to show each page and the exact quote, with the extracted text marked inside it. Rows that need review (conflict, ambiguous, unparseable, or a required field not found) are open, marked with a rule and the words "Needs review", and linked from a summary at the top; a conflict lists every candidate with its own quote and prefers none. Failed: the fixed reason; unknown or malformed answers are shown as unavailable, never guessed. Unknown document, no access or malformed ID: the uniform 404. |
| `POST …/documents/{d}/process`   | The form's target (GET is 405). Exact `Origin` (else 403, nothing sent), ID format, session, then `POST` to the API, which is idempotent. Redirects back with a fixed code (`processing=started` only for a new run; `not_scanned`, `blocked`, `processing_unavailable`, `unavailable`, `rejected`); nothing submitted is echoed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `GET …/documents/{d}/processing` | JSON, `no-store`, for the status poller only: `{state, status, attempts, startedAt}` or a bare `state` (`none`, `not_clean` 409, `not_found` 404, `signed_out` 401, `unavailable` 503). It never returns the result, values or quotes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

- **Live status:** while a run is queued or running, a small client component polls the status route (every 2 s for 20 s, then every 5 s, backing off to 30 s after errors, pausing while the tab is hidden, stopping after 10 minutes with a "Check status" link). The state text sits in a `role="status"` region; when the run finishes it announces "Processing finished…" and refreshes the server-rendered page. Without JavaScript the page shows the state and a Check status link.
- **Truthfulness:** values are shown only as the API returned them, with their evidence; there are no confidence scores, progress percentages or edits. The browser never receives more than the status JSON above from the processing routes; the record is rendered on the server and escaped like any other text.
- **Known limits:** no in-document highlighting (quotes only), no reprocessing or retry of a failed run from the web, no free-text editing.

## Review and approval (R1)

On the document page, owners and reviewers review the extracted record and approve it; members see the same page read-only ("Only reviewers can review and approve."). The API and its database decide who may review, number the decisions and refuse stale writes (see `apps/api/README.md`, "Review"); the web shows the API's state and sends plain forms.

- **Decisions** sit next to the evidence they point at, as plain forms (no JavaScript needed): a found field offers Confirm and Mark unknown; a conflict offers "Use this value" under each candidate that has a value, and "Neither — mark unknown"; a required field without a value offers "Confirm unknown". Optional fields without a value are approved as extracted and offer nothing. There is no free text. Each button's accessible name includes its value and field (for example "Use this value: 1 April 2026 for Effective date"); the current decision is stated in words ("Decided: 1 April 2026") and not offered again, and a decided field loses its "Needs review" mark.
- **Approval panel** (`#approval`, above the fields): what still needs a decision (linked), then Approve record once nothing is left. After an approval it shows "Approved as version N" with a Download JSON link; a decision after that shows "Changed since version N was approved" and offers "Approve again as version N+1". Earlier versions are listed under a collapsed "Earlier versions".
- **Stale writes:** every form carries the run and the decision number and version count the page showed; if anything changed since, nothing is saved and the page says so ("This record changed since you opened it…").

| Route                                             | Behaviour                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST …/documents/{d}/review/decisions`           | A decision form (GET is 405). Exact `Origin` (else 403, nothing sent), ID format, session, then a small URL-encoded form with exactly the expected fields (anything else, including free text, is `invalid` and never sent). Redirects back to the field (`#field-…`) with a fixed code: `decided`, `stale`, `run_changed`, `invalid`, `not_reviewer`, `not_clean`, `rejected` or `unavailable`. |
| `POST …/documents/{d}/review/approvals`           | The approve form; same checks. Redirects to `#approval` with `approved`, `unresolved` or one of the codes above.                                                                                                                                                                                                                                                                                 |
| `GET …/documents/{d}/review/approvals/{v}/export` | Streams the approved record from the API as an attachment (`application/json`, `nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, `no-store`, `X-Record-SHA256`); anything but an attachment is refused (502). Malformed versions are 404 without an API call; no session goes to sign-in. Excluded from `src/proxy.ts`, like the PDF download, so its sandbox policy is kept.   |

- **Messages** are fixed texts looked up from the code (`?review=…`): success uses `role="status"`, refusals `role="alert"`; unknown codes render nothing.
- **Checks:** `src/lib/api/review.test.ts` (strict parsing), `src/lib/review/view.test.ts` (which decisions each field offers, approval state), `src/lib/review/handlers.test.ts` (Origin, IDs, session, forms, codes, export headers), and the production-build runtime checks against a fake API (controls per role and state, approval panel, routes, export headers and bytes).
