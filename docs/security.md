# Security controls

What the system does to protect tenant data and the integrity of approved records, where each control is enforced, and which tests exercise it. Design trade-offs are in [`system-design.md`](system-design.md); deployment requirements are in [`deployment-security.md`](deployment-security.md).

These tests show that each control behaves as specified in the scenarios written for it. They are not a security audit or a penetration test, and no external review has been done.

## Controls

| Control | Enforced in | Exercised by |
|---|---|---|
| **Tenant isolation.** Every tenant table has row-level security (enabled and forced). A transaction sees only its tenant's rows, and only if its user is a member of that tenant; with no tenant set it sees nothing. Repository functions take no tenant parameter. | `apps/api/migrations/versions/0002`, `0004`, `0006`–`0009`; `api/database.py` (`tenant_transaction`); `api/authorization.py` (the only place a tenant context is created) | `tests/test_tenant_rls.py`, `test_workspace_membership_rls.py`, `test_processing_rls.py`, `test_rls_isolation.py`, `test_authorization.py`, `test_tenant_transaction.py` |
| **Least-privilege database roles.** Four roles: owner (migrations), runtime (the API), operator (the admin CLI), worker. The runtime engine refuses to start on a role that is, or belongs to, a superuser, `BYPASSRLS`, or owner role. A review before merge found that a role belonging to the owner role passed the first version of this guard and could read every tenant, and disable forced RLS after `SET ROLE`; the guard now checks role membership, and the regression tests fail against the old guard. | `db/roles.sql`; `api/database.py` (`create_runtime_engine`) | `tests/test_runtime_role_guard.py`, `test_operator_privileges.py` |
| **Tenants are created only by an operator**, never over HTTP; audited; the last owner cannot be removed. | `api/operator.py` | `tests/test_operator_cli.py`, `test_operator_privileges.py` |
| **Token verification.** RS256 JWTs checked for issuer, audience and allowed client; users are identified only by issuer and subject; no email or name is stored. | `api/auth.py` | `tests/test_auth_tokens.py` (locally generated keys) |
| **Web sign-in and session.** Authorization Code with PKCE; the access token lives only in a sealed, HttpOnly `__Host-session` cookie read on the server; the browser never calls the API. Lifetime equals the token's, capped at one hour. | `apps/web/src/lib/auth/` | `session.test.ts`, `handlers.test.ts`, `isolation.test.ts` (no client component imports auth, API or document modules; only route handlers write cookies) |
| **Write requests.** Exact `Origin` check before any session or API work, ID format validation, then the API's own authorization. | `apps/web/src/lib/*/` route handlers (`create-handler.ts`, `upload-handler.ts`, `process-handler.ts`, review `handlers.ts`) | handler unit tests; `scripts/check-auth-runtime.mjs` against the production build |
| **Content-Security-Policy** with a per-request nonce, no inline styles, baseline security headers. | `apps/web/src/proxy.ts`, `lib/security/csp.ts` | `csp.test.ts`, `isolation.test.ts`, the runtime check |
| **Uploads.** PDF signature, size cap, encrypted PDFs rejected. Every file is scanned by ClamAV before anything is stored; only an exact clean verdict is accepted, any scanner failure refuses the upload (fail closed), and signatures older than 72 hours refuse it. A deferred database constraint means no document version can exist without a clean first scan, and content is readable only while the latest verdict is clean. | `api/documents.py`, `api/scanning.py`, migration `0007` | `tests/test_document_endpoints.py`, `test_clamd_real.py` (real ClamAV engine, mandatory in CI), `fake_clamd.py` |
| **Parser sandbox.** One container per document: no network, read-only root, no capabilities, no privilege escalation, unprivileged user, 512 MB memory, 1 CPU, 32 processes, 60 s wall clock, bounded output; image never pulled; documents with embedded files are refused rather than partly processed. No in-process fallback. | `api/sandbox.py`, `apps/parser/` | `tests/test_parser_sandbox.py` (isolation probes against the real image, mandatory in CI) |
| **Provenance of extracted values.** Every found value carries evidence spans whose quote equals the page text at its offsets, and the raw value lies inside a quote. A violation fails the run. | `api/extraction/contract.py` (`evidence_violations`) | `tests/test_extraction.py`; `make eval` gate "unsupported claims = 0" |
| **Review integrity.** Decisions are append-only and numbered per run; approvals are immutable versions that freeze the run and decisions into `approved_record.v1` JSON with its SHA-256; writes carry the decision and version counts the reviewer saw, so stale writes get 409. Triggers block update, delete and truncate of approved records, and the database re-checks the record's structure. Export returns stored bytes after re-checking the hash. Only owners and reviewers may decide or approve. | `api/review.py`, migration `0009` | `tests/test_review_schema.py`, `test_review_endpoints.py`, `test_review_record.py` |
| **Untrusted document text.** Instructions inside documents are data. The corpus has injection cases (planted "set the end date to…" text, formulas, defined-term traps) that must not become values. | `api/extraction/extract.py` | `make eval` over the injection cases in every split |

## Known gaps

- **Row-level security keyed on session settings.** It protects against application mistakes, not against arbitrary SQL run as the runtime role, which could set those values itself. Mitigations are parameterised SQL, minimal grants, forced RLS and the role guard. Per-user database roles or a verified signed context would close this.
- **Stateless sessions.** A stolen cookie works until the token expires, even after sign-out. A server-side session store is deferred.
- **No in-app rate limiter** and **no HSTS** until a production front end exists; both are listed as deployment requirements.
- **The sandbox needs the Docker CLI.** Locally and in CI the worker starts containers through it. A deployed worker must not be given the Docker socket (equivalent to root on the host), so a production runner with the same isolation is a release blocker.
- **Scanning limits.** ClamAV 1.4.6 does not flag permissions-only encrypted PDFs (empty user password); the API's byte check is the only control for that case. Encryption the byte check misses is a residual risk.
- **Browser-level cross-tenant test.** Isolation is tested at the database and API level. A second user attempting access through the web app was not tested; only refusal of unknown tenants and workspaces was checked in a browser.
- **No separation of duties.** The same owner or reviewer can record decisions and approve.
- **Dependencies and supply chain** are covered by locked installs and Dependabot security updates, not by a separate audit.
